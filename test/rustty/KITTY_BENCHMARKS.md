# Kitty graphics benchmarks

## Catnip placement updates

`kitty_place` replays Catnip's steady-state pattern: an uploaded RGBA sprite
atlas, cursor positioning, and cropped `a=p` placements with stable image and
placement IDs, pixel offsets, negative z, `C=1`, and `q=2`. Cases contain 128
or 1,024 sprites. Each timed iteration contains **two frames**, alternating
positions while retaining the pixels. Divide times by two for per-frame cost;
throughput counts individual placements.

Rustty and Ghostty receive identical generated bytes. Before and after timing,
both check the image bytes and dimensions, placement count, every ID, anchor,
source crop, pixel offset, z, and cursor position. Setup, image upload, input
generation, validation, process startup and final terminal destruction are
excluded. Timing includes cursor and Kitty parsing plus placement replacement.
It does not measure renderer preparation, GPU work or visible presentation.

```sh
zig build vt-primitives test-vt-primitives \
  -Demit-lib-vt=true -Demit-macos-app=false -Doptimize=ReleaseFast
GHOSTTY_PRIMITIVES_BIN="$PWD/zig-out/bin/vt-primitives" \
  cargo bench --offline -p rustty-vt --bench primitives -- kitty_place --test
GHOSTTY_PRIMITIVES_BIN="$PWD/zig-out/bin/vt-primitives" \
  cargo bench --offline -p rustty-vt --bench primitives -- kitty_place
```

For paired before/after comparisons, build and copy the executable reported by
`cargo bench --offline -p rustty-vt --bench primitives --no-run` at each revision.
Keep the harness, compiler and flags identical. `bench_compare.py` accepts one
Rust executable plus Ghostty, or several Rust executables, and freezes hashes
and raw samples in its output. For example:

```sh
python3 test/rustty/bench_compare.py \
  --before /tmp/rustty-kitty/before --simd /tmp/rustty-kitty/after \
  --ghostty /tmp/rustty-kitty/ghostty --case kitty_place \
  --output /tmp/rustty-kitty/paired
```

Catnip uploads shared-memory images at startup, then moves the retained atlas
placements. Shared-memory compatibility has a separate live test:

```sh
python3 test/rustty/kitty_shared_memory.py \
  zig-out/bin/vt-oracle target/release/examples/parity
```

It recreates each object for each engine because the terminal must unlink it.
The 14 cases check exact decoded pixels, success/error replies and unlinking,
including macOS page rounding, offsets, explicit sizes, RGB/RGBA, PNG, zlib,
queries, quiet mode, ignored chunk flags and rejected ranges/dimensions.
Run outside a sandbox that denies `shm_open`. This checks compatibility, not
shared-memory transfer speed.

## Placement replacement comparison, 2026-10-10

Updating a placement in place removes the previous vector compaction and push
on every sprite move. Frozen before/after binaries use Rust 1.99.0 with the
workspace release profile (thin LTO, one codegen unit); Ghostty uses Zig 0.16.0
ReleaseFast. Measurements ran serially on macOS 27.0.1 arm64, in forward and
reversed engine order, with 50 samples per direction, 0.3 seconds of warmup and
a one-second measurement target. The table pools 100 samples per engine/case
and divides each two-frame iteration by two.

| Sprites per frame | Rustty before | Rustty after | Ghostty | After / before | After / Ghostty |
| --- | ---: | ---: | ---: | ---: | ---: |
| 128 | 104.17 µs | 89.81 µs | 62.17 µs | 0.862× | 1.444× |
| 1,024 | 2,162.98 µs | 889.30 µs | 2,120.22 µs | 0.411× | 0.419× |

At 1,024 sprites, Rustty is 2.43 times faster than before and takes 42% of
Ghostty's time. At 128 sprites it improves 14%, but remains about 28 µs per
frame slower than Ghostty. Both orders show those results: the 1,024-sprite
after medians are 890/889 µs, versus 2,120/2,120 µs for Ghostty. The retained
linear placement lookup still makes large sprite counts scale worse than
linearly; this change removes vector movement without adding another index.

Exact placement/pixel checks passed for both engines before and after every
measurement. Raw samples, frozen binaries, executable hashes, logs and platform
manifest remain in `/tmp/rustty-kitty/paired`; explicit build commands and
compiler versions are in `/tmp/rustty-kitty/toolchains.json`. The earlier
baseline-only run remains in `/tmp/rustty-kitty/baseline`; a mixed-compiler run
is retained under `paired-mixed-toolchains` and excluded from these results.
These results establish placement-feed
performance for these workloads, not complete game frame-rate parity.

## Image lifetime after Glowstorm exit, 2026-10-10

The renderer previously kept source image buffers and atlas uploads after the
terminal deleted the images, and both rendering backends kept their atlas pages.
A second game therefore accumulated another set of resources. Image retention
now follows the visible pane snapshots; frames keep only their image pages,
and the backends release pages absent from the composed frame. Text pages and
unchanged images retain their caches.

A real-game check kept the same PTY session, CPU renderer and Metal renderer
alive across two launches. Each launch used `GLOWSTORM_SCALE=2.2`, a 120×45 grid
at 2× display scale, and five seconds of gameplay before Ctrl-C. Snapshots and
frames were dropped every iteration, and dead `Weak` image handles were dropped
before measuring, since `Weak<[u8]>` keeps the backing allocation alive even
after its last strong owner is gone. The five uploaded images held
249.1 MiB of RGBA data. Measurements ran on macOS 27.0.1 arm64 with the workspace
release profile.

| Resource after returning to the shell | Before, first exit | Fixed, first exit | Before, second exit | Fixed, second exit |
| --- | ---: | ---: | ---: | ---: |
| Live CPU allocations (`malloc_zone_statistics`) | 381.7 MiB | 3.6 MiB | 780.0 MiB | 3.6 MiB |
| GPU atlas capacity | 140 MiB | 4 MiB | 296 MiB | 4 MiB |
| Resident memory | 658.1 MiB | 658.2 MiB | 1,057.0 MiB | 662.9 MiB |

After each fixed exit, all substantial source buffers were released; the one
remaining atlas page held text. The terminal retained one unused 4-byte
placeholder in its alternate screen. Resident memory did not immediately return
to startup levels: `vmmap` showed about 635 MiB in empty malloc regions, while
live allocations were 3.6 MiB. That allocator caching is distinct from the
previous retained image data; the second run reused the freed memory.
The game is dynamic, so these are representative memory observations, not a
controlled comparison of per-frame CPU/GPU time.

To reproduce in Rustty, keep the window and shell open, run the following twice,
press Enter to start each game, play for five seconds, and exit with Ctrl-C:

```sh
GLOWSTORM_SCALE=2.2 GLOWSTORM_GOD=1 /path/to/catnip/target/release/glowstorm
```

Use `footprint <rustty-pid>` and `vmmap -summary <rustty-pid>` from another
terminal after each exit to distinguish live allocations, empty malloc regions
and graphics memory. The one-off harness, frozen baseline/fixed executables,
source and JSONL samples are retained in `/tmp/rustty-catnip-memory`.
Persistent lifecycle checks cover renderer ownership and backend page release:

```sh
cargo test --offline -p rustty-render -p rustty-render-software -p rustty-render-wgpu
```

The GPU checks require access to a graphics adapter. Ghostty's image deletion
and renderer cleanup paths were used as a reference; this measurement does not
establish whole-process memory parity with Ghostty.

A focused warm CPU-prepare comparison used the same frozen title/gameplay
snapshots with both renderer versions linked into one release binary. With
500 warmups and 100 alternating paired samples of 100 prepares each, title
preparation measured 18.30 → 20.12 µs and gameplay 24.38 → 25.74 µs; fixed timings
include `retain_images`. The paired median cost increases were 1.83 and 1.36 µs.
This measures CPU preparation only, including frame destruction, and makes no
GPU or frame-rate claim. Source, manifests, compiler version, executable hash
and raw samples are in `/tmp/rustty-catnip-memory/prepare-timing`; the initial
smoke run performed during an app build is excluded.

## Shared image pixels and wave 100, 2026-10-11

`kitty_upload` feeds four identical or distinct RGBA images into four live
terminals, timing parsing, base64 decoding and image installation. Setup,
teardown and validation are excluded. Checks compare every byte, count distinct
pixel allocations, and verify no strong owner survives dropping the terminals.

```sh
cargo +1.95.0 bench --offline -p rustty-vt --bench primitives -- kitty_upload --test
cargo +1.95.0 bench --offline -p rustty-vt --bench primitives -- kitty_upload
```

Baseline `a157749e2` and fixed binaries use identical benchmark source, Rust
1.95.0, lockfiles and release flags (thin LTO, one codegen unit), on an Apple
M4 Max with macOS 27.0.1 arm64. Serial runs used both engine orders,
30 samples per order, 0.3 seconds of warmup and a one-second
minimum target (about four seconds for large cases). Medians pool 60 samples;
**each time covers four uploads**.

| Image size | Pixels across terminals | Before | Shared pixels |
| --- | --- | ---: | ---: |
| 256 KiB | Unique | 7.97 ms | 7.66 ms |
| 256 KiB | Duplicate | 7.99 ms | 7.67 ms |
| 4 MiB | Unique | 128.15 ms | 122.25 ms |
| 4 MiB | Duplicate | 128.57 ms | 123.46 ms |

Duplicate payload storage falls from four allocations to one: 1 MiB → 256 KiB
and 16 MiB → 4 MiB; unique payloads keep four allocations. The global index holds
weak `Arc<Vec<u8>>` references, allowing the last strong owner to free the pixel
buffer. These source-payload savings do not measure GPU texture memory.

Real Glowstorm ran with `GLOWSTORM_WAVE=100 GLOWSTORM_GOD=1`, scale 2.2, a 120×45
grid and 2× display scale. The harness pressed Enter, held fire, and rendered
changed frames through Metal for 30 seconds. Shared-memory uploads carried
268.8 MiB, including a 202.4 MiB floor. Startup took 277.8 / 290.7 ms before/after,
including sprite construction and queries; this does not isolate upload cost.

| Wave-100 observation | Before | Shared pixels |
| --- | ---: | ---: |
| Changed frames rendered | 1,776 | 1,787 |
| Peak placements / image quads | 123 / 128 | 131 / 138 |
| CPU prepare median / p95 | 0.336 / 0.440 ms | 0.257 / 0.447 ms |
| GPU submit + wait median / p95 | 1.470 / 1.802 ms | 1.443 / 1.951 ms |
| Live CPU allocations after exit | 4.35 MiB | 4.46 MiB |

Both released substantial game image buffers and returned to one 4 MiB text
atlas. Submit + wait is CPU-observed submission/completion, without GPU
timestamps. These dynamic runs do not establish a frame-time speedup.
`/tmp/rustty-kitty-dedup/after-wave100.png` was visually checked: wave 100,
boss, player, projectiles and glow render correctly. Native-window interaction
remains unverified.

For a controlled warm CPU comparison, both versions replayed the same saved
peak frame: 123 placements, 187 total quads, and matching geometry/color/paint
hashes. With 500 warmups and 100 samples of 100 prepares in each engine order,
median preparation was 42.34 → 42.40 µs (p95 44.62 → 43.87 µs), including
`retain_images` and frame destruction. Image loading is outside that timing.
There is no meaningful warm-prepare change in this workload.

Frozen sources/binaries, hashes, lockfiles, raw samples, logs, screenshots and
the peak-frame fixture are in `/tmp/rustty-kitty-dedup`, including temporary
`stress.rs` and `warm.rs` harnesses. The persistent upload benchmark is
`test/rustty/kitty_upload_bench.rs`.

## Tix per-cell graph scrolling: first profile

The supplied `rustty-tix-kitten-graphics.trace` records 29.55 seconds while
scrolling Linux history. Of 24,505 weighted CPU samples, 90.33% are on the PTY
reader and 83.76% are inside Kitty deletion. The deletion filter contributes
45.63% and orphan cleanup 35.32% (inclusive samples overlap). CPU render
preparation accounts for 3.69%; WGPU preparation for 0.64%.

Instruments also reports 20 main-thread stalls of at least 250 ms, totaling
6.832 seconds. During the longest, 593 ms stall, the PTY thread uses 593 ms CPU,
including 576 ms in deletion, while the main thread uses 2 ms. This is
consistent with the PTY holding the terminal lock while the UI waits.
The exported samples and analysis are in `/tmp/rustty-tix-perf`.

The captured Tix version used ordinary one-cell placements, deleting changed
tiles with `a=d,d=n,I=<image number>,p=<cell placement>` before replacing them.
Previously every deletion calculated each placement's image bounds and searched
the screen rows, then hashed all placement keys to check for relative children.
The first fix (`8164664a9`) calculates geometry only for positional selectors,
avoids collecting image IDs for lowercase deletes, and skips orphan indexing
when no relative placements remain. Placement storage and protocol lifetimes
are unchanged.

Ghostty's exact placement deletion uses a hash lookup, but its orphan cleanup
still scans all placements. This first Rustty fix retains linear placement
scans; it removes the unnecessary geometry, row-search and hashing costs
without adding another mutable index.

The installed Tix binary was replaced during this investigation, after the
original capture. Replaying those saved bytes keeps the Rustty comparison
independent of Tix's simultaneous fix. The synthetic benchmark deliberately
replaces every cell and measures a full-redraw stress case.

An isolated PTY capture navigated a shared mirror of the Linux repository,
leaving its source refs and state untouched. It reached 5,659 live placements
and Tix's 1,024-image cache limit. Two saved redraws contain no image uploads:

| Captured redraw | Live placements / images | Deletes / places | Before | After |
| --- | ---: | ---: | ---: | ---: |
| Narrow | 3,471 / 449 | 1,208 / 1,245 | 118.78 ms | 13.72 ms |
| Wide | 5,151 / 1,024 | 2,591 / 2,595 | 359.59 ms | 41.46 ms |

These are five-sample medians of terminal feed time (8.65× / 8.67× faster).
Setup is excluded; serialized screen state, images, pixel hashes and placement
geometry match before/after for all ten measured outputs. The capture, frozen
replay sources/binaries, raw samples and reproduction steps are in
`/tmp/rustty-tix-graph/README.md`. The updated Tix binary still emits the same
Kitty command counts for the first 50 and 100 navigation inputs; later event
coalescing differs, so this does not measure the benefit of Tix's own change.

The persistent `kitty_cells` benchmark uses 80 rows, with 32 lanes / 256 images
or 80 lanes / 1,024 images. Each iteration applies two complete redraws, deleting
and replacing every tile with another image number. Placement IDs encode
`((row << 16) | column) + 1`, as in Tix. Both engines receive the
same bytes and verify image pixels, numbered IDs, placement geometry, cursor,
and cleanup outside the timed section. Throughput counts tile updates; each
update has two Kitty commands.

```sh
zig build vt-primitives test-vt-primitives -Demit-lib-vt=true \
  -Demit-macos-app=false -Doptimize=ReleaseFast
GHOSTTY_PRIMITIVES_BIN="$PWD/zig-out/bin/vt-primitives" \
  cargo +1.95.0 bench --offline -p rustty-vt --bench primitives -- kitty_cells --test
GHOSTTY_PRIMITIVES_BIN="$PWD/zig-out/bin/vt-primitives" \
  cargo +1.95.0 bench --offline -p rustty-vt --bench primitives -- kitty_cells \
  --sample-size 10 --warm-up-time 0.1 --measurement-time 0.3
```

Matched before/after binaries use Rust 1.95.0 and the same lockfile; Ghostty uses
Zig 0.16.0 ReleaseFast. Frozen binaries, compiler versions, checksums, raw samples
and run scripts are in `/tmp/rustty-tix-perf/synthetic`. Runs are sequential,
with reversed engine order and 20 pooled samples per case. Setup, image uploads,
validation and cleanup are excluded from timings.

Median command-processing time per complete redraw (one half of an iteration):

| Tiles / images | Rustty before | Rustty after | Speedup | Ghostty |
| --- | ---: | ---: | ---: | ---: |
| 2,560 / 256 | 215.65 ms | 32.22 ms | 6.69× | 22.99 ms |
| 6,400 / 1,024 | 1,383.12 ms | 196.31 ms | 7.05× | 132.57 ms |

These deliberately redraw every tile. That Rustty version remains 1.40–1.48×
slower than Ghostty here, and both still scan placements per command. Very
large complete redraws remain expensive; these results are not an end-to-end
scrolling rate.

The existing placement-only controls show no meaningful regression: 128 sprites
take 87.85 → 86.74 µs/frame; 1,024 sprites take 878.64 → 882.70 µs/frame.

Validation includes 114 VT unit tests, 19 renderer graphics tests, and 2,061
placement comparisons with Ghostty, including positional deletes, numbered and
anonymous IDs, relative children, placeholders and scrollback. The regression
test also checks upper/lowercase keyed deletion with duplicate image numbers
and transitive relative children. The release app bundle was rebuilt and signed.

## Tix per-cell graph scrolling: indexed placements

`rustty-slowdown-on-tix-scroll.trace` still spent 34.11% of sampled CPU in the
deletion filter, 12.25% checking for relative placements, and 11.55% placing images. The PTY
reader accounted for 79.26% of sampled CPU. These remaining placement scans
motivated a key-to-slot index alongside the dense placement vector. Exact
deletion and replacement now use that index; deletion swaps the last entry
into the vacated slot and repairs its index. A relative-placement count avoids
scanning for parents when there are none. Positional/bulk deletion and numbered
image resolution still scan their respective collections.

The baseline is `b5941cc5f`, which already includes the first optimization.
Both Rust executables use Rust 1.95.0, identical benchmark sources and lockfiles,
thin LTO and one codegen unit, on macOS 27.0.1 arm64. The unchanged Ghostty
reference uses Zig 0.16.0 ReleaseFast. Runs were serial, with no competing builds,
and included both engine orders. Sources, executable hashes, compiler version,
raw samples and reproduction scripts are frozen in `/tmp/rustty-tix-second/bench`.

The same saved pre-Tix-fix redraws measure terminal processing independently
of subsequent producer changes. Medians pool ten samples per engine/redraw:

| Captured redraw | Live placements / images | Before | Indexed | Speedup |
| --- | ---: | ---: | ---: | ---: |
| Narrow | 3,471 / 449 | 13.72 ms | 2.01 ms | 6.83× |
| Wide | 5,151 / 1,024 | 41.16 ms | 5.98 ms | 6.88× |

Only feeding the redraw is timed. Setup, terminal cloning and validation are
excluded; copy-on-write page detachment caused by retaining the initial clone
is included equally. All 40 measured post-feed outputs match exactly in
serialized screen state, image metadata, image-pixel hashes and placement
geometry. Neither selected redraw uploads images.

The unchanged controlled full-redraw stress cases pool twenty Criterion samples
per engine/case, ten in each order. **The following times are per complete

| Tiles / images | Before | Indexed | Speedup | Ghostty |
| --- | ---: | ---: | ---: | ---: |

Indexed Rustty is 8.27–9.89× faster than the Ghostty reference in these full-redraw

The index trades memory for lookup speed: approximately 24 bytes of live

## Tix page scrolling: image cache eviction

`rustty-slow-scrolling-lots-of-tiles.trace` records the indexed-placement version
at `a888599af`. Active scrolling averages 113.3% of one CPU. The PTY reader
accounts for 77.1% of all samples; renderer preparation accounts for 3.2%.
Whole-image deletion still rebuilds the placement index after removing any
placements: hash-map insertion under deletion accounts for 20.5% of all CPU.
Image-number resolution is another 11.5% and is unchanged by this patch.

A fresh capture of Tix `db3f70c` confirms that its synchronized page updates
exercise this path. Twenty PageDown events emit 12,622 image-wide `d=N` deletes
without placement IDs, in addition to keyed placement deletes. Peak state is
1,722 images and 5,960 placements. These deletes sometimes remove displaced
placements still visible to the terminal, so they cannot simply be skipped.

`Placements::retain` now visits entries backwards and uses the existing keyed
swap removal. Only removed keys and moved slots need index updates; survivor
keys are no longer reinserted after every image eviction. Backwards iteration
visits every original placement once, including when the last entry moves into
a removed slot. Placement order was already unspecified, and rendering sorts
by z-order, image and placement ID. No additional index or allocation is added.

Two complete frames from the fresh Tix capture measure the effect with actual
uploads, cache evictions and placement changes. Ten samples per engine/frame
run in balanced before/after and after/before order. Only feeding the frame is
timed; setup, cloning, canonical state checks and teardown are excluded.

| Captured page frame | Before | After | Speedup |
| --- | ---: | ---: | ---: |
| 936 image evictions, 238 uploads, 4,335 placements | 51.555 ms | 27.202 ms | 1.90× |
| 795 image evictions, 1,493 uploads, 5,778 placements | 71.081 ms | 45.009 ms | 1.58× |

All 40 measured outputs match exactly after canonicalizing unspecified
placement/image iteration order, including complete pixel buffers, image
identity, placement geometry, screen state, modes and counters. These results
are saved with frozen sources and binaries in
`/tmp/rustty-tix-third/replay-final`.

The persistent `kitty_image_delete` benchmark starts with 6,400 placements and

screen state and complete recovery after replacement uploads. Rust 1.95.0

## Tix page scrolling: whole-image deletion

Whole-image `d=I/N` deletion without a placement ID already removes every
placement of its target. Delete that image directly instead of scanning the
surviving placements again. The final scan still applies to orphaned child
images: those can have independent placements that must survive. This also
applies to the implicit deletion before replacing an explicit image ID.

The latest trace attributes 3.81% of process CPU to the redundant final scan.
Relative to the image-number index at `3cd3f0792`, the two-line change measures:

| Captured page frame | Before | After | CPU time before → after |
| --- | ---: | ---: | ---: |
| 936 image evictions, 238 uploads, 4,335 placements | 17.581 ms | 14.798 ms | 17.571 → 14.799 ms |
| 795 image evictions, 1,493 uploads, 5,778 placements | 37.031 ms | 36.855 ms | 37.031 → 36.856 ms |

The eviction-heavy page improves 15.8%; the upload-heavy page is essentially
unchanged. Both engine orders show the eviction improvement. There are 40
samples per engine/page, with exact canonical equality across all 160 outputs.
The same compiler, lockfiles, release flags, capture and timing scope apply.

The persistent deletion benchmark pools 60 samples per case, 30 in each order,
with 0.5 seconds warmup and two seconds measurement per order:

## Tix and Glowstorm: reuse staging buffers for small uploads

The Metal System Trace recorded at 14:45 on 2026-10-12 matches the release
executable at `667bd8238` by UUID. Rustty's GPU activity intervals cover 16.9%
of the 21.44-second recording. Fragment rendering takes at most 1.79 ms, but
upload blits reach 34.43 ms after a burst of 5,729 texture uploads. The trace
contains 164,918 temporary texture-upload buffer allocations. Its 42.62 GiB
Resource Size total combines allocation and free events; it is neither
resident memory nor transferred pixels. Metal tracing accounts for 425 ms of
the 1,127 ms sampled inside `write_texture`, so uninstrumented runs are needed
to measure the benefit of changing that path.

Captured Tix output confirms that these are many small new uploads: 98.5%
are 16×30 RGBA regions containing 1,920 bytes, including their pixel border.
There are no repeated atlas revisions or generation resets in the replay.
The WGPU backend already shares atlas textures and batches adjacent instances,
but `Queue::write_texture` allocates a temporary Metal buffer per region.

The renderer now uses WGPU's existing `StagingBelt` for preparations whose new
uploads are all at most 64 KiB after row alignment. Its reusable chunks are
1 MiB, capped by device limits. Preparations with larger uploads retain the
queue-write path, keeping large image transfers out of the retained pool.
The whole preparation uses one path because queue writes execute before
encoder commands; mixing them could reorder overlapping updates. Small
uploads use a lazily created transfer encoder, submitted before preparation
returns, including on errors. The host may discard its own encoder when
surface acquisition fails; that must not lose uploads whose revisions are
already retained. Large-upload and unchanged preparations add no submission.
Old revisions continue to skip uploads.

and instrumentation counters, without a profiler. Each run retains CPU/GPU
